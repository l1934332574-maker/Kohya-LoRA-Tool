# 稳定性回归记录 · 2026-10-26

## 范围与结论

比较 v0.19.14（提交 `3df1794`）和当前 v0.19.19 工作区（基于 `fc8c5a0`，包含尚未提交的修复）。仅做本地调查、修复和隔离构建，没有发布，也没有覆盖实际安装或训练数据。

本轮发现一处 GPU 实际回归：Fizgig v8.9.6 混合 BF16/INT8 块交换可能破坏权重精度。另修正了图片读取错误的分类和提示。原始测试套件中还存在多项过时的模拟数据和断言，已同步并补充回归用例。

自动检查通过不代表所有模型完成了训练验收。v0.19.14 和新版原始套件均存在失败，不能直接用失败条数评价产品稳定性，也不能因此否定用户反馈。

## 发现与处理

### 1. 混合精度块交换会破坏 BF16 权重

- 本地 GPU、Fizgig v8.9.6 原源码的最小复现失败：`block 22 dtype corrupted: torch.int8`。
- 两个小层复现即可触发，无需大模型；量化层带 LoRA 包装，普通层为 BF16。
- 新源码已有逻辑名称匹配，仍缺少交换前的 dtype/shape 兼容检查。软件以前针对 v8.5.0 的保护未覆盖 v8.9.6。
- 软件启动训练前验证源码，补齐 CUDA 和通用交换路径的保护。名字、形状或精度不同就使用独立搬移，避免复用不兼容存储。
- 保留引擎版本；补丁前备份、异常回滚、同步本地校验记录，重复调用不重复修改。未知或校验失败的源码不做盲目替换。
- 已在独立源码副本运行 GPU 验证：两条交换路径、启用/关闭 pinned memory、各三轮往返，权重输出与原始值逐项相同。
- 本轮没有修改实际安装的引擎。AMD 硬件尚未实测。

相关文件：`kohya_core/fizgig_engine.py`、`kohya_core/fizgig_adapter.py`、`tests/test_fizgig_offloading_compat.py`、`tests/test_moss_offloading_gpu.py`。

### 2. 图片统一保存和错误诊断

- 训练副本统一保存为重新编码的 PNG；修正 EXIF 方向、处理透明通道并去掉旧元数据，原图保持不变。
- Pillow 失败时，在能识别图片格式且满足安全上限的情况下尝试 Windows 解码器。
- 无权限与无法解码分别提示，保留原始异常类型；明显不是图片的文件不进入额外解码流程。
- 批量检查汇总所有坏图；失败不会替换已有多角色训练目录。
- 已验证透明 PNG、调色板 PNG、EXIF JPG、扩展名不符、同名文件、标签保留，以及重新打标时手工遮罩和审核决定的保留。
- 已验证带 EXIF 图片导入遮罩后，方向、尺寸和目标训练图一致。
- 未取得先前用户机器上的原始坏图，因此不能声称修好了那张具体文件。

相关文件：`kohya_core/image_io.py`、`preprocess.py`、`kohya_core/multi_character.py`、`kohya_core/loss_masks.py`、新增图片与多角色测试。

主要过时内容：桥接模拟对象未实现设置存储、伪 safetensors 不是合法文件、续训样本缺权重/调度器/RNG、旧引擎默认版本、弹窗模拟对象缺生命周期方法、断言仍要求偷偷修改用户填写的分辨率/采样间隔。

同步测试数据时保留产品校验：使用隔离设置目录、合法文件头和完整状态结构；不放宽正式代码以兼容测试。增加显式精度不支持时应拒绝、保留明确参数，以及不适用的视频工具应被拒绝的断言。测试窗口销毁前取消自身延迟回调，避免后续测试收到失效的 Tk 回调。
