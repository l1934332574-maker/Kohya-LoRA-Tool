# MOSS / Fizgig 续训快照漏检 · 2026-10-27

## 用户反馈与源码核对

用户提供群聊截图：磁盘存在 `moss_image_lora-000006-state`，重新打开训练时没有续训提示。用户已自行修改检测代码，但本轮没有取得其补丁、训练状态目录或运行日志，不能确认其具体改法及最终恢复步数。

当前 `find_fizgig_state` 已匹配 `<output_name>-六位数字-state`，并非只支持 `-step数字-state`。确定的源码缺陷是目录白名单只包含 v7.0.1、v7.3.1、v8.5.0，未覆盖当前 v8.9.6。与此同时，引擎写入代码将快照保存在 `snapshots/fizgig-<version>/`；保存和发现路径不一致，导致该目录的快照不会进入候选列表。

另外，运行时身份与完成标志的处理也只列出上述旧版，新版使用旧版的成品文件时间判断，而没有使用它自己保存的 `kohya_complete`。存在跨版本候选进入或状态被成品时间过滤的风险。

## 修复

- 保留输出根目录、snapshots 根目录兼容；动态枚举其下 `fizgig-*` 一层目录，覆盖当前及以后版本。避免递归扫描整个输出树。
- 对明确选择的非 v6.5.0 引擎，按 `kohya_runtime.version` 与 family 过滤候选；保持后续训练入口更完整的 runtime identity 校验。
- 对带运行时身份的新版本统一使用完成标志与目标 epoch 判断；保留旧版与无版本调用的成品时间行为。
- 完整快照的权重、优化器、RNG、元数据文件检查继续使用原实现。未更改引擎安装、快照文件或原训练数据。

## 范围与验证边界

本轮仅做源码调查、修复、Python AST 语法及 diff 空白检查，未新增或运行测试，未实跑 GPU 续训、未打包或发布。截图不能证明远端完整状态可恢复；真正恢复还需要原始快照与原训练参数一致。

`gui/modern_host.py::_resume_path` 对 `training_kind=multi_character` 仍按原设计不提供续训；本次未启用多角色续训，也未改变这个边界。本次修复适用于实际走 Fizgig 快照发现入口的训练模式。
